## What
- Queue: removing a row then coming back to the page no longer shows the row again when a queue read left before the
  delete answered and came back after it.
- Practice log: « Not saved. Try again. » at 23:59, Save again after midnight: one entry, dated the day of the first
  try (same client id, same `done_on`; the duplicate key 23505 counts as saved, as before).
- Queue removal pending when the page is hidden or closed (`visibilitychange` hidden, `pagehide`): the DELETE goes
  at once with `fetch(…, {keepalive: true})` to `<backend>/rest/v1/requests?id=eq.<id>`, with the access token
  supabase-js last gave (`onAuthStateChange`, kept in memory). No token, or one that expires within 30 s: supabase-js
  as before. The toast ending (page open) still uses supabase-js.

## Why
Debt lines of `docs/audit-design/COORDINATION.md` (#28 Codex pass 4, #32, #28).

## Decisions
- Stale read: `removed` map id -> `queueGen` at the DELETE's answer; a read with `gen <=` that value drops the row, the
  first read sent after it clears the entry (modelled on `localGen` of L19).
- Practice log: a try is reused for the same text and key whatever the time (the day condition is gone). No migration:
  the client `id` was already sent since #32; only the midnight case was left.
- Direct DELETE: a refused answer (not 2xx) or a network error puts the row back with « Could not remove it: try again
  in a moment. » (if the page is still there to show it).
- Harness: `document.addEventListener` now records its listeners; `page.doc(type, props)` fires them; `page.win(type)`
  fires every listener of the type (two `pagehide` listeners: queue and notes).

## Pitfalls
- What the harness cannot show: whether a real iPhone lets the request leave. iOS Safari freezes a page put in the
  background within moments; `keepalive` lets a request already issued finish, it does not issue one. The fix removes
  the awaits supabase-js puts before `fetch` (session read, possible token refresh), so the request is issued in the
  same task as the event. Not covered: the request is cross-origin with `apikey` / `Authorization` headers, so it
  needs a CORS preflight, and how WebKit treats a keepalive request with a preflight on a closing page is not
  something the harness (or Chromium) can show. To check once on Laurent's installed PWA: remove a row, close the
  app before the toast ends, reopen: the row is gone.
- A device whose token expired while offline falls back to supabase-js (refresh first), as before.
