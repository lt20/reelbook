### What contradicts or completes the spec
1. **`identities: []` did not happen.** With confirmation on, a confirmed address gets HTTP 422 `user_already_exists` on this version.
   The app takes both as `exists`.
2. **Wrong and expired are one answer** (403 `otp_expired`). The app tells them apart by the date of its own last send: an hour or
   more, « expired ». A code replaced by a newer one reads as « wrong », whose text already says « of the latest email ».
3. **`verifyOtp` type `recovery` fires `PASSWORD_RECOVERY`** in the same call. `flowHold` is set before the call, so neither that event nor
   `SIGNED_IN` opens the app before the password is saved.
4. **« Too soon » also answers a repeated `signUp`.** Same address again within the minute (« change address », back): the code screen, with the
   server's seconds in the countdown, and the password typed last still wins after the code.
5. Supposed and confirmed: a second `signUp` does not change the password. Hence `updateUser` after the code.
6. **A person with a pending account, the beta full, who types the form again**: `beta_seats()` is read first (L31), so the waiting list shows
   though Auth would accept. Sign-in still works (right password → new code). Rare, left as it is; say so if it comes up.

## Decisions taken in the lot
- One form, one `screen` at a time, painted by `paintAuth()`; texts in `AU_EN` and `landing.js`, generated from one table so FR and EN are the mockup's.
- The password is only ever in `heldPw` and the field. `rb.pending` holds email, type, date, origin, `verified`, backend URL (a pending of another backend is dropped).
- `verified` in `rb.pending`: from the moment the code is accepted until the password is saved, a reload stays on `set-password`. An account whose email differs from the session's never gets that screen.
- A session arriving without this form's `verifyOtp` (a link, another tab) ends the wait; the password in memory is applied only for the same address, outside the callback.
- `guardedAuth(client, call, args)`: the one place for L42's token. `tests/auth-screens.test.cjs` fails if one of the four calls is made elsewhere.
- Countdown from the server's seconds when it gives them; the `too many attempts` lock lifts itself after 5 minutes (`token_verifications` window), the button comes back.
- Own backends: « a code or a link », no auto-send, up to 10 digits, a mail address without a dot accepted, no contact link.
