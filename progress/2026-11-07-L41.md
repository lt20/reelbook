### What contradicts or completes the spec
1. **`identities: []` did not happen.** With confirmation on, a confirmed address gets HTTP 422 `user_already_exists` on this version.
   The app takes both as `exists`.
2. **Wrong and expired are one answer** (403 `otp_expired`). The app tells them apart by the date of its own last send: an hour or
   more, « expired ». A code replaced by a newer one reads as « wrong », whose text already says « of the latest email ».
3. **`verifyOtp` type `recovery` fires `PASSWORD_RECOVERY`** in the same call. `flowHold` is set before the call, so neither that event nor
   `SIGNED_IN` opens the app before the password is saved.
4. **« Too soon » also answers a repeated `signUp`.** Same address again within the minute (« change address », back): the code screen, with the
   server's seconds in the countdown, and the password typed last still wins after the code.
5. Supposed and confirmed: a second `signUp` does not change the password. Hence `updateUser` after the code.
6. **A person with a pending account, the beta full, who types the form again**: `beta_seats()` is read first (L31), so the waiting list shows
   though Auth would accept. Sign-in still works (right password → new code). Rare, left as it is; say so if it comes up.

## Decisions taken in the lot
- One form, one `screen` at a time, painted by `paintAuth()`; texts in `AU_EN` and `landing.js`, generated from one table so FR and EN are the mockup's.
- The password is only ever in `heldPw` and the field. `rb.pending` holds email, type, date, origin, `verified`, backend URL (a pending of another backend is dropped).
- `verified` in `rb.pending`: from the moment the code is accepted until the password is saved, a reload stays on `set-password`. An account whose email differs from the session's never gets that screen.
- A session arriving without this form's `verifyOtp` (a link, another tab), for the same address on a sign-up: `set-password`, nothing written from it (Codex, pass 1: a password held in a tab may be older than one saved elsewhere, and a pre-registered one must not survive). `USER_UPDATED` from another tab ends that screen. The same for a link with `type=signup` in the address and nothing remembered (Codex, pass 2): **on an own backend, confirming by link now asks for the password once more**, the one change those backends see, so a pre-registered password does not survive. A `verified` pending outlives the code's hour, for as long as a session is there or stored (Codex, pass 3: offline restart). `savePassword` reads the session first and gives up if it is another account (pass 3: another tab).

**Codex: 3 passes used, the third `bloquant` on c1db228; its two findings are fixed in the following commit, not reviewed again** (no fourth pass without the coordinator).
- `guardedAuth(client, call, args)`: the one place for L42's token. `tests/auth-screens.test.cjs` fails if one of the four calls is made elsewhere.
- Countdown from the server's seconds when it gives them; the `too many attempts` lock lifts itself after 5 minutes (`token_verifications` window), the button comes back.
- Own backends: « a code or a link », no auto-send, up to 10 digits, a mail address without a dot accepted, no contact link.

### Grants: measured, out of this lot, nothing changed
On a fresh stack with `schema.sql` as its only migration, `has_table_privilege` for `authenticated` answers false on select, insert, update and delete for 10 of the 11 tables: `account_quotas`, `beta_daily`, `beta_settings`, `beta_waitlist`, `notes`, `practice_log`, `requests`, `sessions`, `sheets`, `user_themes`. `capture_tokens` has its own explicit grants (select, delete and column-level insert and update).

With a real `authenticated` token, PostgREST answers code `42501`, message `permission denied for table user_themes` (the same for the other nine, each with its own name). `capture_tokens` answers 200.

The cause: `pg_default_acl` of role `postgres` gives `anon` and `authenticated` only `Dxtm` on tables. Control on the same fresh stack with `auto_expose_new_tables = true`: `sheets` and `user_themes` true, `beta_settings` false (its `revoke` still applies). The comment of `config.toml` from the CLI says unset is « the new cloud default » and that the field goes away on 2026-10-30.

Of the ten, `beta_daily`, `beta_settings` and `beta_waitlist` are closed on purpose. The six tables the app reads directly (`notes`, `practice_log`, `requests`, `sessions`, `sheets`, `user_themes`) are the problem, plus reads of `account_quotas`, if `schema.sql` is meant to allow them (it only revokes writes there). **Not measured on a real cloud project** (no hosted read in this lot): the cloud part rests on that CLI comment alone.
